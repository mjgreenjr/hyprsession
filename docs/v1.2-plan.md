# hyprsession v1.2 — implementation plan (ordered placement)

Base: `main` @ `4c8bab0`. Contract: `V1_2_BRIEF.md` (problem statement, DEC-A/B/C and acceptance
criteria are taken as given). **Status (amended after spike #1): plan only — no implementation exists on this branch.** Spike #1
(§1.4) landed on outcome-table **row 4**: reading-order insertion cannot converge, so the queue
design in §3 is **dead as written** (its order key is wrong; see the banner in §3). **DEC-A and
DEC-B stand unchanged; DEC-C is closed** (dwindle, `force_split = 2`). A second spike (§9) tests
whether a *computed* insertion order can reproduce a saved tree; §9.6 states what §3 becomes if it
succeeds and the close-out if it fails. **Rulings received after the spike #2 amendment:** DEC-B is *relaxed* (switching the visible workspace
during a load is acceptable **if the placement technique requires it** — conditional, not a preference:
prefer hidden operation where it works; focus still returns to the starting workspace). DEC-D is
*approved in principle* as part of the float/unfloat technique below; the shipped default is decided on
spike #2 data. A first-hand disclosure (§1.4, "Post-spike information") adds an **unfloat variant** to
spike #2 Part B (§9.4.1). Spike #1 is recorded in §1.4 and in full in
`docs/v1.2-spike1-report.txt`; the spike scripts are `scripts/spike-v1.2.sh` and
`scripts/dwindle_model.py` (+ `scripts/test_dwindle_model.py`).

## 0. What the code does today (relevant facts, read from `src/load.rs` @ 4c8bab0)

1. **Launches are already sequential and in reading order.** `run_load` walks `plan.entries`
   (ordered by `launch_order`: workspace, floating-last, x, y) and, per entry: records the live
   address set, sends `Op::Exec`, then polls up to `LAUNCH_WAIT_TICKS` (80 ticks = 20 s) until a new
   mapped window appears, claiming windows on every tick; then `fulfil_group` (V3 settle +
   re-invocation) runs before the next entry launches. So for single-window groups, arrival order
   is *already* launch order, i.e. reading order of each group's first saved window. The brief's
   "arrival order is app launch latency" therefore bites only where claiming or arrival departs from
   launch order: multi-window groups, windows slower than the 20 s wait, late V3 re-invocations,
   and — see item 3 — claim identity.
2. **Placement is immediate.** `place_live` calls `Placer::assign` then `apply` (→
   `plan_adjustment` → `Op::MoveToWorkspace` …) for each unclaimed live window on every poll. A new
   window is born on the *visible* workspace and is moved off it (silent) within one tick (250 ms).
3. **Claiming is by class (then exact title) in saved order, not by "the window I launched for this
   save".** Two foot windows launched for saves S2 then S1 (reading order S1, S2) are claimed
   S1-slot-first if S1 precedes S2 in `clients.json`, regardless of which launch produced which
   window. Two same-class terminals can therefore swap slots with no change to the
   class/workspace/argv multiset's *membership* — and with distinct `--working-directory` argv they
   are visible in the six-field fingerprint. This may be a second source of the measured
   divergence besides insertion order. The brief freezes claiming, so the plan does not change it;
   the spike is designed to tell the two causes apart (§1.3, outcome table row 1).
4. **Which op is order-sensitive.** In dwindle only *insertion into a workspace's tree* is
   order-sensitive. For a tiled window the insertion is the `MoveToWorkspace` the loader sends
   (the window first split the *visible* workspace's tree when it mapped). `MoveWindow`/`Resize`
   are only issued for floating windows. A tiled window already on its target workspace (the
   workspace that was visible when the load started) emits no move at all — see OQ-1.

## 1. The spike (runs first; Mike runs it on the real machine)

### 1.1 What it answers

Brief §3 questions, made operational:

* **Q-S1 Divergence reproduced?** Does save A → load A → save B → load B → save C with current
  code give a non-empty six-field diff on a small tiled fixture? (diff(A,B) and diff(B,C))
* **Q-S2 Split target on a hidden workspace.** When windows are moved one by one onto a hidden
  workspace, which existing leaf does each insertion split — the most recent arrival (geometry
  advances like a spiral) or a pinned remembered window? The script prints the workspace's window
  table after every single move, so the target of each split is readable from which rectangle
  shrank.
* **Q-S3 Do reading-order moves alone converge?** Prototype of the v1.2 behavior done outside
  hyprsession: launch all windows, hold them on the visible workspace, then move them onto the
  scratch workspace in saved reading order, twice (A→B′→C′). Run for **forward** and **reverse**
  launch/arrival order: if the result does not depend on arrival order, a queue that flushes in
  reading order is effective.
* **Q-S4 Is holding on the visible workspace needed?** Variant with held windows parked on
  `special:spike-stage` (a hidden special workspace) instead of the visible one — same final
  geometry or not.
* **Q-S5 Pause between moves.** Does the result change with `SPIKE_STEP_PAUSE=0` vs `0.5`?
* **Q-S6 The visible-workspace case.** With `SPIKE_ACTIVE_CASE=1` the scratch workspace is the
  visible one; moves are no-ops, which is what a load experiences for the starting workspace.
* **Q-S7 (DEC-B data, opt-in).** `proto-focus` repeats the prototype but focuses each window after
  moving it, which flickers the visible workspace. It exists only so that, *if* the other variants
  fail to converge, the DEC-B ruling can be made with data. Not run by `all`; not used by the design.
* **Environment (DEC-C):** the script prints `general:layout`, the `dwindle:*` options that steer
  splits (`use_active_for_splits`, `force_split`, `preserve_split`, `smart_split`,
  `split_width_multiplier`) and workspace rules. If any scratch/real workspace runs master, it is out of scope.

### 1.2 Safety

* Uses **one scratch workspace** (`SPIKE_WS`, default 9, must be empty) and requires the
  **visible workspace to be empty and different** (new windows land on it before being moved).
  Refuses otherwise.
* The hyprsession loads are `load <name> --workspace 9` (v1.1 scoped load): only workspace 9's
  windows are closed and launched. The prototype only closes windows on workspace 9.
* `hyprsession save` is desktop-wide, so snapshots contain real titles; they live under
  `/tmp/hs-spike` (outside the repo), the fingerprint/diffs are restricted to workspace 9, the
  pasted report contains fixture paths only, and `cleanup` deletes the directory.
* Guard added after spike #1: `baseline`, `proto` and every other command that closes windows on the
  scratch workspace first require that **every** window there is one of the script's own foot
  fixture windows (`--working-directory=$SPIKE_DIR/cwd/…`); otherwise the script refuses and names the
  pid. `cleanup` closes fixture windows only. (Spike #1's `baseline` lacked this guard; `preflight`
  already required an empty workspace.)
* No file from a real desktop is ever committed. `export-fixture` writes only the foot fixture
  windows of the scratch workspace (class, geometry, argv with `/tmp/hs-spike` paths) for the
  committed bench fixture; review before committing.

**Prototype (hold, then move in saved reading order), first cycle, forward/stage 0 — per-move tables.**
Reading order of A is `[d1 (TL), d3 (BL), d4 (BM), d2 (R)]`. Inserted in that order, the tree grew:
`#1` alone → `#2` splits `#1` (side by side, #2 right) → `#3` splits `#1` (stacked, #3 below) →

**T = [1, 1, 3]** (step 2 splits #1, step 3 splits #1, step 4 splits #3), and the slot filled by

different occupants: **the prototype reproduces the baseline's rotation exactly; reading-order

**Cross-checks printed by the script.** forward/stage 0 vs reverse/stage 0, first cycle: EMPTY.
forward/stage 0 vs forward/stage 1, first cycle: EMPTY.

**Data-quality notes.**

1. **Discounted — reverse/stage 0, second cycle.** Its log header reads "held on workspace 12": the

2. **Not covered by the two printed cross-checks — reverse/stage 1 deviates in both of its cycles.**

   sequence differed in that variant. The pointer position and focus history were not logged in
   spike #1 (hypotheses H-pointer and H-focus below). This does not change the row-4 ruling (the

**Post-spike information (first-hand disclosure from the user).** The user's hand-grown layouts —
the `s3l` shape (full-height left, stack right) included — are *never* grown by move-insertions. He

which Part A still has to characterise (needed for the fallback path); (2) his saved shapes need not be
in the family the compositor grows by plain moves at one pointer position, which is why reading order
and even a computed move order can fail for them; (3) the technique he uses by hand — float, hover,
unfloat — is itself a candidate placement technique (§9.4.1, unfloat variant). The DEC-B and DEC-D
rulings that follow are in §9.8.

## 3. Design (SUPERSEDED AS WRITTEN — spike #1 landed on row 4; conditional on spike #2, see §9.6)

> **Banner.** §3 designed the queue with reading order as the order key. Spike #1 shows reading order
> cannot converge, so as written it must not be built. What survives (the claim/place decoupling, the
> per-workspace hold list, the flush conditions, floaters on claim, the V3/scoped/adjust-only
> interplay, the reports, `--simulate`) is retained **if spike #2 succeeds**, with one change: the order
> key becomes a *computed insertion index* (reading order only as the fallback). §9.6 lists the exact
> amendments. If spike #2 fails, §3 is not built at all. Read the rest of §3 with that substitution.

### 3.1 Module layout

| File | Change |
|---|---|
| `src/queue.rs` (new) | `PlacementQueue`: per-workspace hold list, expected counts, reading-order key, flush selection. Pure data + decisions, no `Host`; fully unit-testable. |
| `src/load.rs` | `Placer::assign_indexed` / `release`; `place_live` holds tiled claims; `run_load` drives flush points; `flush_workspace` issues the held windows' placement ops; `LoadReport` gains `ordered`/`on_claim` counters. `launch_order` untouched. |
| `src/session.rs` | `simulate_load` prints the per-workspace placement order; load report line. `plan_adjustment` untouched. |
| `README.md` | Short note under "Window counts and reports". |
| `tests/` | Synthetic bench fixture (from the spike) and integration test. |

No new `Op`, no new `Host` method (see 3.9 for the one possible exception).

### 3.2 Claim vs place

Claiming is unchanged: `Placer::assign(live) -> Option<Client>` keeps its signature and matching
rules. A thin `assign_indexed(live) -> Option<(usize, Client)>` (target index + saved client) is
added and `assign` delegates to it, so existing placer tests stay byte-for-byte valid. A
`release(index)` clears `matched` for a held window that vanished before its flush, so the tail
loop may claim a replacement.

`place_live` still returns the addresses **claimed** in this pass (not "placed"), so V3's phase
counting (`settle_group`, `fulfil_group`) and the claimed-address set used by V5 surplus see exactly
what they see today.

### 3.3 What is deferred, what is not

A claim is **queued** iff the saved client is tiled: `!saved.floating`, and its workspace is not the
anonymous special (-99, which `plan_adjustment` skips anyway), and the load is in place-by-class
mode. Everything else is placed on claim exactly as today: floating windows (their `Float`/`Move`/
`Resize` ops are pixel placement and not tree nodes), legacy `place_by_class == false` loads (queue
never constructed), windows claimed after their workspace flushed.

What is deferred is the **whole `apply` for the window** (all ops `plan_adjustment` yields: move to
workspace, workspace→monitor, float correction, pin, fullscreen), computed at flush time against the
window's *fresh* live state, not the state at claim — so a window that has since moved or changed is
diffed correctly. The ops of one window stay together and in their current relative order.

### 3.4 Queue state

```rust
pub struct PlacementQueue {
    expected: HashMap<WsKey, usize>,          // tiled saved clients per workspace (from plan.saved)
    held: HashMap<WsKey, Vec<Held>>,          // claimed, tiled, not yet placed
    pending: HashMap<WsKey, usize>,           // launch entries that may still produce windows for this workspace
    flushed: HashSet<WsKey>,                  // workspaces whose queue has been flushed
}
struct Held { saved_index: usize, saved: Client, live: Address }
type WsKey = (i32, String);                   // workspace (id, name): named specials share id -98
```

* `expected[ws]` — count of tiled saved clients on `ws` in `plan.saved` (the slice, in a scoped load).
* `pending[ws]` — number of launch entries whose `GroupInfo.saved` include a window on `ws`
  (an entry spanning several workspaces counts for each). An entry with **no** group info (possible
  in tests/legacy-shaped plans while `place_by_class` is true) is treated as pending for *every*
  workspace until it ends — conservative, never early.
* Built once at the top of `run_load` from `plan.entries` + `plan.saved`.

### 3.5 Reading order

`fn reading_key(at: (i16, i16), saved_index: usize) -> (i16, i16, usize)` — x, then y, then saved
index as the deterministic tie-break. This is the `launch_order` key minus the floating flag (queued
windows are all tiled) applied to saved clients, with the workspace grouping provided by the per-workspace
lists. `launch_order` is not modified (v1.1 launch behavior frozen); a unit test asserts the two keys
agree on tiled entries so they cannot drift apart.

Multi-monitor: coordinates are layout-global, so the key is consistent within a workspace
(a workspace lives on one monitor).

### 3.6 Flush conditions and points

A workspace `ws` is flushed (its held list sorted by `reading_key`, then placed in that order)
when, evaluated **at the end of a claim pass** and **at the end of a launch entry's phase**:

1. **Complete:** `held[ws].len() == expected[ws]` (every tiled save for `ws` is claimed), **or**
2. **Phase over:** `pending[ws] == 0` — every launch entry that could produce a window for `ws` has
   finished its phase (launch wait + `settle_group` + V3 re-invocations, or failed to launch), so no
   more windows are coming from the deadline machinery already in place.

and `ws` has not flushed yet. After a workspace has flushed, later claims for it are placed on claim
(late arrivals, V3 re-invocations that outlived the phase, slow apps), as the brief specifies;
the existing shortfall and surplus reports describe them unchanged.

Call sites in `run_load`:

* in the per-entry poll loop and in `settle_group`, after each `place_live` pass: evaluate rule 1
  (count reached) — rule 2 cannot fire mid-phase for the workspace of the entry being launched;
* when an entry's phase ends (after `fulfil_group`, or after a failed `Op::Exec`): decrement
  `pending` for the entry's workspaces, then evaluate rule 2 for them;
* when the entry loop finishes: every workspace has `pending == 0`, so all remaining held windows
  flush before the tail loop begins;
* in the tail loop: after the entry loop every workspace is flushed (`pending == 0`), so a window
  claimed in a tail pass is a late arrival and is placed on claim; held lists stay empty. In
  `--adjust-clients-only` (no entries) every workspace starts with `pending == 0`: the first pass
  claims the existing windows and the end-of-pass evaluation flushes them in reading order;
* a final unconditional `flush_all` before computing unmatched/surplus and before the focus return,
  as a safety net (no held window can survive `run_load`).

**Interaction with V3.** Re-invoked newcomers are claimed during the same entry's phase, so they sit
in the same held list and are placed in reading order with their siblings. `claimed` counting is by
claim, so `fulfil_group`'s decisions are unchanged (a held window still counts as claimed).

**Interaction with the settle/deadline machinery.** No new timers: the flush rides the existing
`LAUNCH_WAIT_TICKS` / `SETTLE_TICKS` / `plan.tail_ticks` bounds. A workspace whose group never
produces its full count flushes at the end of that group's phase, not after a new wait.

**Scoped loads (`--workspace N`).** `plan.saved` is already the slice, so `expected`/`pending` cover
only N; `protected` windows are never claimed so can never be held; the flush moves only N's windows.
Nothing else changes.

### 3.7 Flush mechanics

```
flush_workspace(host, placer, queue, ws, report):
    live = host.clients()                       // one read per flush
    for held in queue.take_sorted(ws):           // reading order
        match live.find(held.live):
            Some(window) => { apply(host, window, held.saved); report.placed += 1; report.ordered += 1 }
            None         => { placer.release(held.saved_index); println!("Warning: …") }
    // PENDING-SPIKE (Q-S5): host.pause() × FLUSH_PAUSE_TICKS between windows, default 0
```

`apply` is the existing function (no change). `report.placed` is now counted at placement (flush)
rather than claim; every existing assertion on `placed` is on a path where flush happens before
`run_load` returns, so the totals are unchanged.

### 3.8 Layout scope (DEC-C)

Dwindle only. The loader does not query the layout today and the brief does not ask for a runtime
probe; for a master-layout workspace, holding then flushing in reading order is harmless (the final
moves are still issued, only later) and neither claimed to help nor to hurt. Spike row 10 decides
whether a guard is needed; default: none.

### 3.9 Held windows' whereabouts

By default held windows stay where they were born (the visible workspace) until their workspace
flushes — at most for the duration of one workspace's launch phase, since launches run in
workspace order. This is visible churn on the user's current workspace in a scoped load (v1.1 also
shows each window there, but only for one tick). **Optional** staging on a hidden special
workspace is PENDING-SPIKE (row 6) and not part of the default design.

The start-workspace case (OQ-1): a window destined for the workspace that was visible when the load
began issues no move, so it cannot be reordered by the queue; it keeps its arrival position.
PENDING-SPIKE (row 7).

## 9. Spike #2 — pin the split-target rule, then compute an insertion order

### 9.0 What spike #1 changes about the problem

The prototype grew the same tree shape in every clean cycle and only the *occupants* of its slots
rotated. If the shape depends only on the insertion count and external state (not on which window is
inserted), then **an insertion order can never change the tree — it only decides who sits in which
slot.** Two consequences, both to be tested rather than assumed:

* For a saved tree that equals the shape the compositor grows for its window count (the fixture does:
  `[TL, R, BL, BM]`), the right order is the *slot* order (`d1, d2, d3, d4`, the build order), not reading
  order. This is the reviewer's finding: the tree grows as a deterministic function of insertion
  count, so a saved tree is reproducible by a computed order.
* For a saved tree that is **not** the shape the compositor grows at the current external state
  (a hand-grown layout; or the mirror image "full-height on the left, stack on the right"), **no
  insertion order exists**. Only steering the external input that picks the split target could help. Spike
  #2 therefore also measures which input that is — and the DEC-B/DEC-D implications of steering it.

* **The user's own shapes.** Per the disclosure in §1.4, his layouts were grown by float/hover/unfloat
  insertions, i.e. with the pointer choosing each split. They are therefore expected to be reachable
  by *pointer-steered* growth, and — unless he happened to leave the pointer in the right place — not by
  plain moves at one pointer position. §9.4.1 adds an unfloat variant that reproduces his technique.

The reverse/stage-1 anomaly in §1.4 (note 2) shows that the target is *not* a function of count alone,
so the rule has to be pinned first (Part A) before the computation (Part B) means anything.

### 9.1 Hypotheses formed from the §1.4 data

All rules choose a leaf to split; the new window becomes its second (right/bottom) child
(`force_split = 2`) and the split runs along the leaf box's longer side. They differ only in the choice.
Spike #1 gives, per variant, targets in insertion-index terms:

| Variant (cycle 1) | T (steps 2,3,4) |
|---|---|
| forward/s0, reverse/s0, forward/s1 (stepwise tables); the baseline loads A and B and the hand-built fixture reach the same final shape | **[1, 1, 3]** |
| reverse/s1 (both cycles) | **[1, 1, 1]** |

| Hypothesis | Rule (function of tree state + one external input) | Fits [1,1,3]? | Fits the anomaly? | Predicts |
|---|---|---|---|---|
| **H-pointer** | the leaf whose box is nearest the mouse pointer (0 if inside); ties → oldest | yes, pointer in the bottom-left region | yes, pointer in the top-left region | T depends on pointer area; independent of arrival/stage |
| **H-focus** | the leaf of the compositor's last-active window if it is on this workspace, else a fallback | unknown | plausibly (the last-launched window differs between reverse and forward arrivals; staging changes focus history) | T depends on arrival order / staging at a fixed pointer |
| **H-state** | a function of tree/insertion history only (e.g. a fixed traversal order) | needs a rule that picks #1,#1,#3 | **no** — unless the anomaly cell is contaminated | T identical in every run with the same N |
| refuted by the data | oldest (always #1); newest (always the previous arrival); largest-area; smallest-area | no | – | (unit-tested in `test_dwindle_model.py`) |

*Additional evidence for H-pointer (first-hand, §1.4):* the user's unfloat insertion splits the leaf
under the pointer. That does not by itself show that a `movetoworkspacesilent` insertion onto a hidden

### 9.2 Part A — fixtures and protocol (`./scripts/spike-v1.2.sh rule`)

No hyprsession loads: windows are launched (they land on the visible workspace), held, then moved onto
the scratch workspace one at a time in a stated insertion order, with **window table, pointer
(`hyprctl cursorpos`) and active window (`hyprctl activewindow`) recorded around every move**. The script
derives the split target of each step by diffing consecutive tables (exactly one pre-existing window's
rectangle changes per insertion) and writes one JSON line per run to `runs/rule.jsonl`. A run is marked
*discounted* automatically if windows land on the scratch workspace before the first move or the visible
workspace changes (the spike #1 contamination), and discounted runs are excluded from scoring.

| Block | Runs | What varies | Discriminates |
|---|---|---|---|
| **P** pointer matrix | N=5, forward, insertion 1..5, pointer parked at TL, TR, BL, BR, C | pointer only | H-pointer vs the rest: if T differs by area as in §9.1 → pointer rule; if identical across areas → pointer irrelevant |
| **A** arrival × staging | N=5, pointer parked at BL, {forward, reverse} × {stage 0, 1}, **two repeats** each | launch order and staging only (pointer fixed) | H-focus vs H-pointer: T varying inside A at a fixed pointer → focus/launch-history; the spike #1 anomaly cell (reverse/s1) is repeated twice, so a reappearance with a *logged fixed pointer* kills "the pointer moved" |
| **N** count scaling | N = 2, 3, 4, 6 at pointer BL and TR | count | the rule's generalisation; supplies slot sequences for N=3,4,6 |
| **R** repeatability | N=4, BL, identical run ×3 back to back | nothing | hidden state / hysteresis (run 2,3 differing from run 1) |
| **O** permuted order | N=5, BL, insertion order `3 1 5 2 4` | *which* window is inserted when | identity-independence: T (in insertion-index terms) must equal the forward N=5 BL run; this is the premise of slot matching |

**Pointer handling.** `SPIKE_POINTER=auto` (default) tries to warp the pointer (`movecursor` in classic
dialect; a guessed `hl.dsp.cursor.move({x,y})` in lua — unverified, the script logs whether it worked and
re-reads `cursorpos`); if the warp is not accepted it asks you, once per area, to park the physical
pointer in a named screen region and press Enter. `SPIKE_POINTER=manual` always asks; `ignore` only logs
(the measurement of the pointer still happens). Warping the pointer is a spike-only convenience here;
the loader does not do it (see DEC-D, §9.8).

**Reading the result** (the `score` table plus the per-run `T=` lines):

| Observation | Stated rule | Next |
|---|---|---|
| H-pointer matches all non-discounted runs except possibly C; A cells agree with each other at the fixed pointer | **R-pointer:** `target(leaves, p) = argmin over leaves of dist(p, box)`, ties → oldest | Part B with `rule=pointer` |
| T identical across P (pointer irrelevant) but varies inside A | **R-focus:** depends on launch/focus history | write the rule from the A/N tables; Part B needs a focus-history model — and if steering needs focus on the scratch workspace that is the **DEC-B stop** |
| T identical in every run for a given N (A anomaly did not reproduce) | **R-state:** a single shape per N | slot-matching algorithm only (no external input); reachable family = {S_n}; anomaly recorded as a one-off |
| nothing fits | – | paste `rule.jsonl`; analysis offline; no Part B |

### 9.3 The stated rule (to be filled from the run)

The rule is stated as a function of tree state: `target = F(leaves = {(id, box)}, ext)` with `ext` the
external input identified by Part A. Nothing in Part B is hard-coded to one candidate: `dwindle_model.py`
takes the rule by name (`SPIKE_RULE`, default = the scorer's BEST). The run's `rule.best` and the
`rule.jsonl` it was scored on are pasted back and recorded here as §9.3.1 before Part B's results are read.

### 9.4 Part B — computed insertion order (`computed`, `bar`)

**Algorithm** (implemented in `scripts/dwindle_model.py order`, ~100 lines; to be ported to Rust only
after a GO):

1. *Select* the workspace's tiled windows from the snapshot (`floating == false`, argv present); recover
   the layout box as their bounding box grown by the outer gap (12 px: `gaps_out`).
2. *Reconstruct the saved tree* by recursive guillotine partition: for the window set, find the cut
   line (vertical, then horizontal; preferring the orientation of the longer side) that no rectangle
   straddles (tolerance 24 px: the 14 px gap plus the ≤5 px rounding seen in the data), choosing the cut
   nearest the box centre (dwindle splits 50/50). Output: nested `(orientation, first, second)` with
   leaves = windows; failure (overlap, no cut) → fallback.
3. *Simulate the growth* of n windows under the stated rule and the current external input, with the
   same split geometry (longer side, second child = new window), yielding the shape `S_n` and which
   insertion index fills each leaf.
4. *Match* `S_n` against the saved tree structurally (orientation and child order, not pixels). On
   success the mapping window → insertion index **is** the order (insert index 1 first). On failure the
   tree is unreachable at this external input → **fallback: saved reading order**, with the reason
   printed.
5. **Steer variant** (`computed … steer`, needs `SPIKE_ALLOW_POINTER=1`): walk the saved tree breadth
   first; each internal node, in turn, is the next split; before inserting its second child's window,
   warp the pointer to the node's box centre so the (confirmed) pointer-nearest rule picks that leaf.
   Every dwindle tree is reachable this way. This is **not** part of the default design: it moves the
   user's pointer (DEC-D, §9.8).

`order` prints `MODE computed rule … | MODE fallback <reason>` and the windows in insertion order; exit
status 3 means "fallback".

**Prototype in the script.** For a snapshot `shape-NAME`: close the scratch workspace's fixture windows,
launch the shape's windows (they land on the visible workspace), move them onto the scratch workspace in
the computed order (window table after every move), save `computed-NAME-MODE`, and print
`RESULT computed[NAME,MODE]: PASS|FAIL`. PASS = six-field `diff(saved, reproduced)` **EMPTY on the first
cycle** — immediate reproduction. A failing shape prints its diff and its per-move tables in the report;
none is dropped.

**Success bar (stated in advance).** First-cycle six-field diff EMPTY for **every** shape tried:

| Shape | Built by | Why it is in the bar |
|---|---|---|
| `s4` — the original 4-window shape | insertion (pointer BL) | the spike #1 fixture; must pass if the premise holds |
| `s3r` — 3 windows, full-height RIGHT + stack on the left | insertion | the shape the compositor grows at BL |
| `s3l` — 3 windows, full-height LEFT + stack on the right | **by hand** on the visible scratch workspace | the user's real ws4/ws7 pattern; the mirror of `s3r` |
| `s5`, `s6` — 5- and 6-window shapes | insertion | scaling |
| `h5` — a 5-window layout you actually use | **by hand** | a hand-grown tree |

*Do not drag dividers when arranging the hand shapes:* dwindle splits 50/50 and the loader cannot set
ratios, so a resized divider would make an EMPTY diff impossible for a reason outside this item.

**Prediction recorded before the run (so that the result can falsify it).** If the rule is H-pointer,
`s4`, `s3r`, `s5`, `s6` pass in plain mode (they were grown at the pointer the order is computed for),
while `s3l` and `h5` **fail in plain mode** with a `MODE fallback … unreachable` line (the tree is not
the one the compositor grows at that pointer) and pass only with `steer`. The bar as written
("every shape EMPTY") would then be met **only by steering the pointer**, which is now approved in
principle (DEC-D) *as part of the float/unfloat technique* (§9.4.1); whether steering ships by default is decided on this spike's data. If the rule is H-state, `s3l`/`h5` are unreachable by any means
and the bar cannot be met for hand-grown layouts. These outcomes are reported, not argued away.

#### 9.4.1 Unfloat variant (the user's technique) — `unfloat NAME [hidden|visible]`, `unfloat-bar`

Added after the user's disclosure and the DEC-B/DEC-D rulings. For a shape snapshot `shape-NAME`:

1. Close the scratch workspace's fixture windows (guarded: fixture windows only).
2. Compute the **steer schedule** with `dwindle_model.py steer`: the windows in growth order and, for each
   insertion after the first, the centre of the leaf box that must be split (breadth-first over the saved
   tree, boxes from the model's own splits, in global coordinates).
3. Launch the shape's windows (they land on the visible workspace), **make each floating where it was
   born, then move it onto the scratch workspace** — floating windows are not tree nodes, so the scratch
   workspace's tree stays empty.
4. **Unfloat them one at a time in schedule order**, before each unfloat (after the first) warping the
   pointer into the target leaf's *current* box; record the window table of the tiled windows, the
   pointer and the derived split target after every unfloat (`runs/unfloat.jsonl`, `T=` lines).
5. Save `unfloat-NAME-MODE`; `RESULT unfloat[NAME,MODE]: PASS|FAIL` with **PASS = first-cycle six-field
   diff EMPTY**; a failure prints the diff and the per-step tables. The pointer's original position is
   restored at the end.

* **Mode `hidden` (first):** the unfloats happen on the non-visible scratch workspace; pointer positions
  are global coordinates. No workspace switch.
* **Mode `visible` (only if hidden fails):** the script switches the visible workspace to the scratch
  workspace for the unfloats and back to the starting workspace afterwards, and **logs that it did so**
  (`VISIBLE MODE: switched … / switched back …`). Permitted by the DEC-B relaxation; the script still
  requires an explicit `SPIKE_ALLOW_SWITCH=1`. `unfloat-bar` tries visible mode only for shapes that
  failed hidden.
* **Shapes:** `s3l` and `h5` — predicted unreachable by move insertion — are the test; `s4` is the
  control (it passes by plain computed order, so a failure of the control would indicate a problem with the
  technique itself, not with the shape).
* **Needs:** `SPIKE_ALLOW_POINTER=1` (it moves the pointer). Pointer warp is attempted with the same
  dialect-specific dispatch as `computed … steer` — classic `movecursor`, lua `hl.dsp.cursor.move` (a
  **guess, unverified**; the script logs whether the compositor accepted it). If warping is not accepted
  the script asks you, per step, to park the pointer at a described screen position (percent across/down)
  and press Enter, so the technique is still testable by hand; but a shippable version needs a working
  warp dispatch, which is why the log of that is part of the result.

Part A (the `rule` run) is unchanged: plain-move behaviour must still be characterised for the fallback
path.

### 9.6 Part C — what §3 becomes

#### 9.6.1 Outcomes of the unfloat variant (decides the flush technique)

| Unfloat result (`s3l`, `h5` test; `s4` control; first-cycle diff EMPTY) | What the design's flush becomes |
|---|---|
| **Passes hidden** | Per workspace, claimed tiled windows are **floated and moved onto it** (float-enable, then the existing move), and at the flush are **unfloated in the computed (steer) order, warping the pointer into the target leaf's current box before each unfloat**; no workspace switch. The pointer position is saved before and restored after (DEC-D, approved in principle); with no working warp dispatch the design falls back to the next row. The order key is the steer schedule (any dwindle tree is reachable); reading order remains only for trees that do not reconstruct. New in `Host`/`Op`: pointer warp and cursor read; `Op::Float` already exists. |
| **Passes only visible** | **Per-workspace visible processing**: at each workspace's flush the loader switches the visible workspace to it (DEC-B relaxed, because the technique requires it), unfloats in steer order with pointer steering, and moves on; the starting workspace is refocused at the end (A2). Every switch is logged; workspaces with no queued tiled windows are never visited; workspaces are processed in order to minimise flicker. |
| **Fails both** | **Part B stands as written**: plain computed order (reachable shapes), reading-order fallback with a reported reason; the steering question returns to the **DEC-D default of no**. If the plain computed order also fails the bar for the reachable shapes, the close-out below applies. |

Two cautions regardless of row: a shape that passes proves the technique on that shape only; and a window
that cannot float (fullscreen, or a window rule forcing tiling) needs the plain path — the design keeps
both paths and chooses per window.

### 9.8 New decisions, risks and open questions

* **DEC-B — relaxed by the user (conditional).** Switching the visible workspace during a load is
  acceptable *if the placement technique requires it*; not a preference. Prefer hidden operation where it
  works; focus still returns to the starting workspace at the end (A2). Acceptance criterion 5 of the
  brief ("the only focus dispatch is the final return") is therefore met only when hidden operation
  suffices; if visible processing ships, criterion 5 is restated as "the visible workspace changes only
  as logged, and returns to the starting workspace".
* **DEC-D — approved in principle** as part of the float/unfloat technique (§9.4.1); the shipped default
  (on or off, opt-in flag or not) is decided on spike #2 data. Original question, kept for context:
  **may the loader warp the mouse pointer?** Only needed to reach trees
  the compositor would not grow at the pointer as found (hand-grown layouts, mirror shapes). It is not a
  workspace switch, so DEC-B is not violated, but it is a visible side effect the brief does not mention;
  it would need save/restore of the pointer position and an opt-in flag. Default: **no** — plain mode
  plus honest fallback. Spike #2 measures what steering buys so the ruling is data-driven.
* **The external input may not be controllable at all** (focus-driven rule): then reachable shapes are
  those grown at whatever the focus state is, and DEC-B (§2 row 8) applies to any steering.
* **Fragility of a pointer-dependent order.** The user's physical pointer moves; the order is computed at
  flush time for the pointer as found, which may differ from the pointer when the snapshot's tree was
  grown. Fallback rows and reports must make this visible, not silent.
* **Resized dividers.** Hand-grown desks usually have non-50/50 ratios. The loader cannot set ratios
  (brief §2), so those layouts cannot reproduce exactly regardless of order; topology can.
* **Releasability.** `force_split`, `use_active_for_splits`, `preserve_split`, `smart_split` and
  per-workspace layout rules differ between users; the algorithm must read them or fall back.
* **Multi-monitor.** Pointer and layout coordinates are global; the model assumes the pointer is on the
  workspace's monitor. Out of scope for the spike (single focused monitor); fallback otherwise.
* **Orientation ties.** Near-square boxes make the "longer side" rule sensitive to rounding; the
  topological match uses the simulation's own boxes, and Part B's tables will show if any shape trips it.

### 9.9.5 Final rulings

* **DEC-D RATIFIED: ship the placement queue plus computed insertion order ALONE.** No pointer steering,
  no float/unfloat placement, no workspace switching in the loader. (DEC-B's relaxation is therefore
  unused; criterion 5 — no visible switching — stands as originally written.)
* The queue/flush machinery of §3 stands: claiming is decoupled from placing for TILED windows; flush per
  workspace on full claim or the existing settle deadline; moves are applied against fresh live state at
  flush. The order key is the computed insertion order prototyped in spike #2 Part B; saved reading order
  is the fallback. Claiming stays frozen (OQ-3). Floating windows are unchanged (exact geometry, as v1.1).
* **Acceptance (DEC-A): convergence** — save A, load, save B, load, save C; the six-field diff(B, C) must
  be EMPTY including tiled at/size. A-to-B geometry-only differences are tolerated.
* Implementation order: §9.7 steps 1-6 and 8, without step 7 (technique) and without the pointer-related
  `Host` additions beyond what the plain computed order needs (see the implementation notes below once
  written). All live-behavior claims are PENDING until Mike's local convergence playtest.

### 9.9.6 Implementation notes (v1.2 as built)

Built per §9.7 steps 1-6 and 8; step 7 (technique) is not built. All behavior below that touches the
compositor is **PENDING** the user's convergence playtest (`docs/v1.2-handoff.md`).

* `src/dwindle.rs` — pure port of the spike's `order`: `reconstruct` (guillotine tree from rectangles,
  24 px tolerance), `simulate` (pointer-nearest dwindle growth; a pointer equally near two leaves is an
  error, the compositor's tie-break being unknown), structural match, `computed_order`, `reading_order`.
* `src/queue.rs` — `PlacementQueue` (§3.4): expected / held / pending / flushed per `(id, name)` workspace.
  Held = tiled and not the anonymous special (-99). Floating windows are never held.
* `src/load.rs` — `Placer::assign_indexed`/`release`; `place_live` holds tiled claims; a workspace flushes
  at the end of a claim pass when every tiled save is claimed, or when no launch entry that could still
  produce a window for it is left (entry phase over) and something is held; `run_load` evaluates the
  second rule after each entry (also a failed Exec), and a final `flush_all` precedes the unmatched/surplus
  computation, so nothing claimed stays held. Moves are applied through the existing `apply` against
  `host.clients()` read at flush; a window that vanished is `release`d and may be re-claimed (then it is
  placed on claim, its workspace having flushed). `placed` is counted at placement.
* Order key: the order is computed over **all** tiled saves of the workspace (the saved tree); held
  windows are sorted by rank, so a missing window leaves a hole instead of reshaping the rest.
* `Host` gained read-only `cursor_pos()` (`cursorpos`) and `option(key)` (`getoption`), with defaults
  returning `None` (so any host that cannot answer gets the reading-order fallback). Computed order is used
  only when `general:layout == dwindle`, `dwindle:force_split == 2` and the pointer is readable;
  `general:gaps_out` is read for the layout box (default 12). Per-workspace layout rules are **not**
  consulted (known limitation). The pointer is read before the flush and again after; a difference is
  reported (`pointer_moved`), not corrected.
* Reports: one `FlushReport` per flushed workspace (`windows`, `fallback` reason, `pointer_moved`), printed
  after a load; `--simulate` prints, per workspace, that its tiled windows are placed together and the reading
  order (the computed order needs the live pointer, so a simulation cannot show it).
* Not done (by ruling): pointer warp, float/unfloat, workspace switching, staging, `FLUSH_PAUSE_TICKS`.
  OQ-1 stands: windows destined for the workspace visible at load start get no move and keep their arrival
  position. OQ-3: claiming unchanged.
* Tests: 126 → 164 lib tests (new in `dwindle`, `queue` and `load`, incl. arrival-order independence for
  three arrival orders, fallbacks, late arrivals, V3 newcomers, adjust-only, scoped, vanished window,
  pointer drift); integration 22 and doc 2 unchanged.
