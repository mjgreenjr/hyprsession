# Fix round 2 — restore fidelity (`docs/v1.2-fix-brief.md`)

Two defects from playtest stage 1, fixed on `v1.2/plan`. **All live behavior PENDING your re-run of the full
protocol** (fresh A → B → C, both diffs, per-workspace order lines) plus the two scenario checks below. No
compositor here; verified only against synthetic process trees and the fake host.

## Defect 1 — wrapper blindness at save (fixed)

Cause (as the brief found): under the `hyprsession-resume` wrapper the resumed program shares the non-interactive
`sh -c` wrapper's process group, so `capture_terminal` saw "the shell holds the foreground" and recorded nothing;
the recovered command was only used to strip the wrapper from `argv`.

Fix: `capture_terminal` (`src/procfs.rs`) now checks whether the terminal's shell *is still the wrapper*
(`resume::wrapper_program` reads `sh -c <script> hyprsession-resume <cwd> <command>` from the shell's argv). If so
the program is running, and the foreground record is built from the wrapper's own (cwd, command)
(`command_detection::shell_split`, the inverse of `shell_join`). It then flows through the unchanged
`ResumeConfig::decide`, so the table/replay/prompt policy and `linked` semantics are untouched. When the program
ends the wrapper `exec`s the user's shell, whose argv has no marker, so nothing stale is recorded.
Guards kept: hyprsession-itself-in-foreground (own pid among the wrapper shell's descendants → nothing recorded),
the multi-window-process warning/skip, the ambiguous multi-shell skip, and `linked` (a resumed program that owns
another saved window is `linked`, not relaunched).

## Defect 2 — claiming race at load (fixed)

Cause: claiming matched by class then by *title* among all unmatched saves; five saves share `mike@omarchy:~` and a
fresh resume window wears that title until its program retitles it.

Fix (`src/load.rs`, `Placer::assign_bound`): a window that appears during a **resume launch entry's** phase (new
since that entry's `before` snapshot, entry command carries the wrapper marker) is bound first to *that entry's*
saved windows (`group.saved`), regardless of title. Saves belonging to resume entries are *reserved*: a window from
any other source (plain launches, tail, adjust-only) takes them only if nothing unreserved of its class fits.
Claiming for non-resume windows is otherwise unchanged (title, then order). Residual risk: a late window of an
earlier terminal entry that maps during a later resume entry's phase and is the same class could bind to it.

## Where the pointer dependence lives (R2a: established first)

From the repository's own spike data, not from this session (no compositor here): every spike #2 run that
measured the split rule — Part A blocks P/A/N/R/O and every Part B reproduction — moved windows from the visible
workspace onto a **hidden** scratch workspace with `movetoworkspacesilent` / `follow = false` (`probe_run`,
`dsp_move`; the plan requires the visible workspace to be empty and *different* from the scratch one), with the
pointer sitting on the visible workspace. The split target followed the pointer there (pointer matrix, §9.9.1),
and Part B's 12/12 PASS used orders computed for the pointer as found. So the dependence on the on-screen pointer
for silent moves onto a hidden workspace is the *measured* case, not an extrapolation. (The brief's statement that
this was only confirmed on a viewed workspace does not match the protocol the spike ran; the unfloat variant was
the one that used pointer warps.) What the spike did not isolate: whether the warp dispatch itself is accepted, and
whether the pointer must sit inside the target leaf in global coordinates when the workspace sits on another monitor.
Both are covered by the loader's own checks below, so a wrong assumption shows up in the load output rather than
silently.

Why WS9/WS10 broke, then: the saved trees (WS9 flipping between "stack-left + full-height right" and
"full-height left + stack-right") are each only growable at some pointer positions, the loader computed the order for
the pointer as found, fell back to reading order when the tree was not growable there, and reading-order growth
produces a different tree — so the shape depended on where your pointer happened to be.

## What changed

- **Steering (R2/R2a)** — `dwindle::steer_schedule` grows ANY dwindle tree: walk the saved tree breadth first; the
  node being split is a single leaf at that moment, so a pointer at its box centre (strictly inside, never on a
  boundary) selects exactly it. `flush_workspace` warps the pointer there before each insertion
  (`Op::MoveCursor`, Lua `hl.dsp.cursor.move({ x, y })`, classic `movecursor`) and **verifies every warp by reading
  `cursorpos` back** (3 tries). Before the first window of a workspace moves, the first warp is proven; if it is not
  accepted the loader stops steering for the rest of the load, says so, and uses the previous behavior (order for
  the pointer as found, then reading order). The user's pointer is read at load start and **restored at the end**
  (`pointer_home`). The order is computed over the workspace's whole saved tiled set, so a missing window leaves a
  hole.
- **Verification** — after each flush the loader reads window geometry back and reports
  `N of M tiled windows are at their saved geometry` (±6 px); a mismatch is a warning. This is the load's own
  evidence that the tree regrew, and the diagnostic if the pointer assumption is wrong.
- **R3** — a tree produced by the fallback is an ordinary dwindle tree, so the next generation reconstructs and
  steers it exactly: fallback in generation N saves back identically in N+1 (test below). Needing the second
  cycle (WS10's behavior) came from computed-order-at-the-pointer-as-found; steering removes the dependence.
- **R1** — `load` (non-simulate) re-executes itself via `src/detach.rs`: new session (`setsid`), SIGHUP ignored,
  stdin closed, stdout/stderr to `<session dir>/load.log`; the typed command follows the log and returns the load's
  exit code. `HYPRSESSION_NO_DETACH=1` runs in the foreground. Default mode's startup load is not detached (it has
  no terminal). New dependency: `libc` (already in the lock file transitively).

## D2 — the mechanism (required explanation)

I had no compositor, so this is reasoning from the code and the §3 fixtures, with each candidate ruled in or out and
the evidence for it. Where something is inference rather than proof, it says so, and the build now prints what is
needed to confirm it.

**What the evidence shows.** Six workspaces (1, 2, 5, 6, 7, 8) plus the round-2 holdout WS9 came back exact under
steering, with the same centre-of-leaf pointers, the same split rule and the same direction handling as WS4/WS10. So
steering itself works; the failures are workspaces where something other than a clean steered flush produced the tree.

1. **"Insertion in found order rather than the schedule's order" — ruled IN, for exactly two situations.**
   `flush_workspace` sorts the held windows by schedule rank, so a *flush* inserts in schedule order (ruled out for
   that path by reading the code and by the simulated-compositor tests). But the schedule governs only windows that go
   through a flush. A window placed outside one is inserted in arrival order, at whatever pointer position the
   previous steering left: (a) a window claimed after its workspace had already flushed ("late arrivals are placed on
   claim"), and (b) a window destined for the workspace the load started on, which is born in that tree and never
   moved (OQ-1).

2. **WS4 — ruled IN: a workspace was flushed half built, and the hole design could not recover.** The log says WS4's
   phase placed 2 of its 3 saved windows; the third arrived after the phase and was placed on claim. The tree R shows
   (Lions left full-height, the other two stacked on the right) is exactly what insertion order
   `[Lions, third-window, playcall-gui]` produces, not the schedule order `[linked terminal, Lions, playcall-gui]`:
   the schedule's first window is the *occupant* of the root's first leaf, and it was the missing one. Missing the
   occupant of a node means the later windows' pointer targets (the centres of leaf boxes that do not exist yet) land
   on whatever leaf is nearest, and the late window is then inserted at the leftover pointer. My previous design
   ("the order is computed over the whole saved set, so a missing window leaves a hole") was wrong for that case:
   a hole at an internal node's first leaf reshapes everything after it. The transposition is this, not a direction
   or coordinate error.

3. **WS10 — full membership at flush time, yet the wrong shape: ruled IN, as the "staging workspace is also a target"
   candidate; stated as strong inference.** All three WS10 saves had claimed windows (the third being the misbound
   generic terminal), so a clean flush should have produced A's tree with a different occupant — but R's shape,
   `H(codex, V(home, brave))` (a full-width window on top), cannot be grown from an empty hidden workspace on a
   landscape box by any pointer or order: the first split of a 1920×1080 leaf is side-by-side. A window set with a
   horizontal root split exists only if the tree was built *among other windows and then lost them*. That is exactly
   what happens on the workspace the load is started from: every new window is born on the visible workspace, WS10's
   own windows are never moved (no move is issued: OQ-1), and every other workspace's staged windows join and then
   leave that same tree, so its final shape is whatever survived. The A snapshot supports that WS10 was the start
   workspace: it contains the terminal with `wd=Work/hyprsession` — the terminal a `hyprsession load` of this project
   is typed into. I cannot prove it from here; the load now prints `Start workspace: N`, which settles it.

4. **"Split direction vs leaf-centre handling" — ruled OUT as the cause.** If the compositor chose a split direction
   from the pointer's position inside the leaf (smart_split), a pointer at the exact centre would be degenerate and
   would break every steered workspace, not two. The trees on seven workspaces regrew exactly with centre pointers.

5. **"Staging workspace also a target" for *hidden* targets — ruled OUT.** A hidden target's tree is built only at its
   flush, from empty; staged windows live in the start workspace's tree, not the target's.

**Fixes:**
- *No half-built workspaces.* While launches are outstanding a workspace is flushed only when every tiled save of it is
  claimed, or at the very end of the load (after the tail wait). A launch phase ending no longer flushes it, so late
  windows join the same flush and the schedule's first-leaf occupant is present. (`queue.rs` rule 2 now applies only
  when there is nothing to launch: adjust-only.) Cost: windows for an incomplete workspace stay on the visible
  workspace until then (previously until their phase ended); a workspace that really never completes places after the
  tail wait (`--load-time`) rather than after its phase.
- *Start workspace rebuilt.* It is flushed last (after every other workspace has taken its staged windows). If its
  tiled windows are exactly the load's own, they are all moved to a hidden special workspace (`special:hyprsession-stage`)
  and moved back in schedule order with steering. If it holds anything else (adjust-only, scoped loads, a stray
  window) it is left as before and the load warns. No workspace is switched. Tests: the WS10 fixture, a stranger on
  the workspace, and a control that fails without the parking.
- An incomplete flush at the very end (an app that never came) is still approximate; it is reported by D3's check.

## D1 — claiming across entries (identity swap) (fixed where provable)

Mechanism: an entry's phase ended as soon as *any* newly claimed window satisfied its count, and the first new window
that appeared was taken as its own. A slow window from entry X therefore satisfied Y's phase and was claimed by title
against Y's saves; X's own window then arrived "late" for X and took what was left. Cascades off by one (WS3→WS9→WS4).

Fix (`load.rs`): launch provenance from `/proc`. Each entry's command gives the process it starts
(`cd <dir> && prog args` → argv + cwd). A new window's pid is read (`Host::process`) and attributed to the earliest
launched entry whose process it is (argv with basename argv[0], plus cwd); it then binds first to *that entry's* saved
windows regardless of arrival time or title. A window that belongs to a different entry no longer ends this entry's
wait or counts toward its group. Windows whose process matches no entry (single-instance apps whose pid is older,
sandboxes, anything unreadable) are not attributed and use the previous class/title/resume-phase rules, so nothing
regresses for them. Tests: the interleaving case (X slow, Y quick, same class and title: bound correctly, and the
control without provenance reproduces the swap), plus signature/matching unit tests.

**Interaction with §4 (ruled — see "§4 ruling" below; behavior unchanged):** provenance can only distinguish entries whose launch commands
differ. Terminals are launched from the save-time cwd, so two terminals with the same cwd get the *same* command and the
same process signature — they are indistinguishable at launch, and which of them lands on which workspace is arbitrary
(earliest launched entry with room). That is the WS3/WS9 argv-only swaps (two terminals sharing `playcall-gui` as cwd,
differing only in their recorded `--working-directory`), in opposite directions, and it is why they remain after this
fix; under the §4 ruling they are accepted, not defects (cwd is the identity). It is also why provenance and
canonicalisation conflict: canonicalisation erases the one distinguisher provenance would otherwise use.

## D3 — verification once, at the end (fixed)

The per-flush read is gone. After the tail, the final flush, the focus change and the pointer restore, the loader waits
two ticks, reads the geometry once, and reports **per workspace** how many of the *placed tiled windows* (flushed or
placed on claim) are at their saved geometry (±6 px), naming the ones that are not:
`Workspace N: all K tiled windows are at their saved geometry` or `Warning: workspace N: only J of K … (off: …)`.
Because the flush now waits for full membership, a mid-assembly false alarm (WS3's "0 of 1") cannot occur, and a late
arrival is part of the same final read. Test: late window → one flush, one final check, 2 of 2.

## Pointer origin (open question)

`run_load` captured the pointer after `clear()` had closed every window; closing windows changes focus, and with a
focus-follows-cursor-warp setting that can move the pointer, so the "origin" was whatever it was after the clear
(a place like (1866, 121) is where it sits after a focus-driven warp). Now: `RealHost::new` captures it in
`LocalSession::load` **before** the clear (the earliest point inside the load process), `Host::pointer_origin()` returns
that, and the log prints `Pointer at load start: x,y` at the start and `Pointer restored to x,y` at the end. The restore
also moved after the final `FocusWorkspace`, since the focus change itself can warp the pointer. (In a detached load the
child process captures it; the user could in principle move it between pressing Enter and the child starting — a few
milliseconds.) If you still see a different restore point, the two log lines will say which side moved it.

## §4 ruling (Mike): cwd is the identity — closed

Terminal launches are canonicalised by the entry's save-time cwd, not its saved argv. **Ruled correct; it stays.** A
terminal's lived identity is its cwd plus its foreground program; its launch argv (e.g. `--working-directory=…`) is an
accident of how it was opened. No behavior change results. Consequences recorded:
- The WS3/WS9 argv-only differences between A and the post-load save (two terminals sharing a cwd, in opposite
  directions) are accepted, not defects. They are not a pass/fail input for the re-run.
- Terminals with the same cwd and foreground program are interchangeable; which of them lands on which workspace is
  arbitrary by design (D1 provenance resolves entries whose launch commands differ, and is neutral for identical ones).
- Comparison for acceptance should therefore treat a terminal by (cwd, foreground program, workspace, geometry), not by
  launch argv. The existing six-field fingerprint still includes argv; a cwd-normalised comparison was not added (not
  needed unless the argv noise obstructs the re-run).
