# Fix round 2 — restore fidelity (`docs/v1.2-fix-brief.md`)

Two defects from playtest stage 1, fixed on `v1.2/plan`. **All live behavior PENDING your re-run of the full
protocol** (fresh A → B → C, both diffs, per-workspace order lines) plus the two scenario checks below. No
compositor here; verified only against synthetic process trees and the fake host.

## Defect 1 — wrapper blindness at save (fixed)

Cause (as the brief found): under the `hyprsession-resume` wrapper the resumed program shares the non-interactive
`sh -c` wrapper's process group, so `capture_terminal` saw "the shell holds the foreground" and recorded nothing;
the recovered command was only used to strip the wrapper from `argv`.

Fix: `capture_terminal` (`src/procfs.rs`) now checks whether the terminal's shell *is still the wrapper*
(`resume::wrapper_program` reads `sh -c <script> hyprsession-resume <cwd> <command>` from the shell's argv). If so
the program is running, and the foreground record is built from the wrapper's own (cwd, command)
(`command_detection::shell_split`, the inverse of `shell_join`). It then flows through the unchanged
`ResumeConfig::decide`, so the table/replay/prompt policy and `linked` semantics are untouched. When the program
ends the wrapper `exec`s the user's shell, whose argv has no marker, so nothing stale is recorded.
Guards kept: hyprsession-itself-in-foreground (own pid among the wrapper shell's descendants → nothing recorded),
the multi-window-process warning/skip, the ambiguous multi-shell skip, and `linked` (a resumed program that owns
another saved window is `linked`, not relaunched).

## Defect 2 — claiming race at load (fixed)

Cause: claiming matched by class then by *title* among all unmatched saves; five saves share `mike@omarchy:~` and a
fresh resume window wears that title until its program retitles it.

Fix (`src/load.rs`, `Placer::assign_bound`): a window that appears during a **resume launch entry's** phase (new
since that entry's `before` snapshot, entry command carries the wrapper marker) is bound first to *that entry's*
saved windows (`group.saved`), regardless of title. Saves belonging to resume entries are *reserved*: a window from
any other source (plain launches, tail, adjust-only) takes them only if nothing unreserved of its class fits.
Claiming for non-resume windows is otherwise unchanged (title, then order). Residual risk: a late window of an
earlier terminal entry that maps during a later resume entry's phase and is the same class could bind to it.

# Round 3 — placement reproduction (`docs/v1.2-placement-brief.md`)

## Where the pointer dependence lives (R2a: established first)

From the repository's own spike data, not from this session (no compositor here): every spike #2 run that
measured the split rule — Part A blocks P/A/N/R/O and every Part B reproduction — moved windows from the visible
workspace onto a **hidden** scratch workspace with `movetoworkspacesilent` / `follow = false` (`probe_run`,
`dsp_move`; the plan requires the visible workspace to be empty and *different* from the scratch one), with the
pointer sitting on the visible workspace. The split target followed the pointer there (pointer matrix, §9.9.1),
and Part B's 12/12 PASS used orders computed for the pointer as found. So the dependence on the on-screen pointer
for silent moves onto a hidden workspace is the *measured* case, not an extrapolation. (The brief's statement that
this was only confirmed on a viewed workspace does not match the protocol the spike ran; the unfloat variant was
the one that used pointer warps.) What the spike did not isolate: whether the warp dispatch itself is accepted, and
whether the pointer must sit inside the target leaf in global coordinates when the workspace sits on another monitor.
Both are covered by the loader's own checks below, so a wrong assumption shows up in the load output rather than
silently.

Why WS9/WS10 broke, then: the saved trees (WS9 flipping between "stack-left + full-height right" and
"full-height left + stack-right") are each only growable at some pointer positions, the loader computed the order for
the pointer as found, fell back to reading order when the tree was not growable there, and reading-order growth
produces a different tree — so the shape depended on where your pointer happened to be.

## What changed

- **Steering (R2/R2a)** — `dwindle::steer_schedule` grows ANY dwindle tree: walk the saved tree breadth first; the
  node being split is a single leaf at that moment, so a pointer at its box centre (strictly inside, never on a
  boundary) selects exactly it. `flush_workspace` warps the pointer there before each insertion
  (`Op::MoveCursor`, Lua `hl.dsp.cursor.move({ x, y })`, classic `movecursor`) and **verifies every warp by reading
  `cursorpos` back** (3 tries). Before the first window of a workspace moves, the first warp is proven; if it is not
  accepted the loader stops steering for the rest of the load, says so, and uses the previous behavior (order for
  the pointer as found, then reading order). The user's pointer is read at load start and **restored at the end**
  (`pointer_home`). The order is computed over the workspace's whole saved tiled set, so a missing window leaves a
  hole.
- **Verification** — after each flush the loader reads window geometry back and reports
  `N of M tiled windows are at their saved geometry` (±6 px); a mismatch is a warning. This is the load's own
  evidence that the tree regrew, and the diagnostic if the pointer assumption is wrong.
- **R3** — a tree produced by the fallback is an ordinary dwindle tree, so the next generation reconstructs and
  steers it exactly: fallback in generation N saves back identically in N+1 (test below). Needing the second
  cycle (WS10's behavior) came from computed-order-at-the-pointer-as-found; steering removes the dependence.
- **R1** — `load` (non-simulate) re-executes itself via `src/detach.rs`: new session (`setsid`), SIGHUP ignored,
  stdin closed, stdout/stderr to `<session dir>/load.log`; the typed command follows the log and returns the load's
  exit code. `HYPRSESSION_NO_DETACH=1` runs in the foreground. Default mode's startup load is not detached (it has
  no terminal). New dependency: `libc` (already in the lock file transitively).
